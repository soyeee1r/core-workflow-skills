# 业务规则

## 发布触发

- “明确发布”必须是人类完成式陈述或可靠平台记录，不包括计划、催问、预览、待发布、审核通过或机器人转述。
- 只有能关联唯一项目与视频的事件才创建 Publication。模糊简称需结合回复串、项目别名和内容 ID 核对。
- `published_at` 优先采用平台实际时间；平台暂不可读时采用人类明确给出的时间并标记来源，首次进入后台后再核对。
- 人类在群内真实 `@0615` 并明确说明某项目视频已发布时，若项目、平台和内容唯一，直接创建 2h、6h、24h、48h 四个窗口任务，不再二次确认。没有另写发布时间时，暂以该消息 `create_time` 作为 `published_at`，并在首次进入后台后核对。
- 本用户默认 `required_platforms = [douyin, wechat_channels]`。发布消息只有一个平台链接时，也为另一个平台建立 provisional Publication 和四个窗口；首次进入后台后必须用账号、实际发布时间与内容详情唯一匹配并回填，不能只凭相似标题。
- 同一视频跨平台发布时，每个平台/账号各有一个 `publication_id`，每个 Publication 有独立的 2h、6h、24h、48h 快照。

## 2h、6h、24h 与 48h 口径

- 统一使用带时区的实际发布时间；默认业务时区为 `Asia/Shanghai`，平台明确显示其他时区时保留原值并转换。
- `due_at_<window> = published_at + <window>`，四个默认窗口固定为 2h、6h、24h、48h；不得用群消息被捕获时间、计划发布时间或自然日零点替代。
- “明早”“后天早上”等模糊说法不覆盖四个默认窗口；仅当用户明确指定新的采集窗口时，才按该明确窗口更新任务。
- 允许在到期后采集；每个窗口到期后的 6 小时内记为正常执行窗，超过后标记 `late` 并写出实际快照龄，仍应补采。
- 页面数据若注明“截至昨日”“近 7 日”等非实时口径，原样记录口径，不把它称作对应小时窗口的精确数据。

## 指标与证据

- 保存平台原始字段名、显示值、单位、口径说明和可用性；只有定义足够一致时才映射到标准字段。
- 不把缺失、权限不足、页面失败或“--”解释为 0。
- 一次采集至少保留后台截图、导出文件或 API 原始响应之一。证据需能证明内容身份、采集时间和指标值；敏感账号信息按最小范围保留。
- 前台公开点赞/评论可用于交叉核对，不能替代后台专属数据。

## 幂等与冲突

- 业务幂等键固定为 `publication_id:2h`、`:6h`、`:24h`、`:48h`；四者分别确定唯一 `metric_snapshot_id`。
- 同一键重复运行只做回读验证。已有快照与新读数不一致时保留原快照并报告冲突；除非用户明确发起纠错，不覆盖历史。
- 平台晚到修正数据属于新的人工纠错或后续窗口，不伪装成任一既定窗口的首次快照。

## 权限

- 只读后台和向已映射的内部项目文档追加数据属于本次授权范围。
- 登录、短信/扫码/二次验证由用户本人完成；Agent 不索要或保存密码、验证码、Cookie、Token 或恢复码。
- 抖音优先复用用户 Chrome 现有登录态；视频号需要后台访问时，如 Chrome 尚未登录，在原发布触发会话喊用户登录，登录完成后从同一任务恢复。
- 每个项目只保留同一份 `<正式项目名>-数据回收` 飞书文档；按 `project_id` 复用已有文档，不创建独立电子表格或第二份文档。没有文档时在用户“我的文档库/数据回收”目录创建。同一期抖音与视频号、同一平台的 2h、6h、24h、48h 数据都写入一张统一对比表的窗口列，只追加不覆盖；各窗口的涨幅概述也只追加不覆盖。
- 任何发布、编辑、撤回、删除、评论、私信、投流或账号设置操作都不在本 Skill 范围。

## 群内回执

- 每个窗口只有抖音与视频号都写入同一文档并回读一致后，才向原发布群发送项目级“<窗口> 数据回收已完成”阶段回执；附各平台采集时间、指标数和同一文档链接。
- 48h 完成且两个平台的四个窗口全部完成后，该窗口的唯一群消息同时说明双平台四窗口整体复盘已完成；不额外发送第五条消息。文档至少包含各平台指标的 2h/6h/24h/48h 值及相邻窗口增量/增幅。
- 阶段回执按 `project_id:<window>:group_receipt` 去重；48h 的同一幂等键同时作为最终回执，保存发送 `message_id`，重跑不重复发群。
