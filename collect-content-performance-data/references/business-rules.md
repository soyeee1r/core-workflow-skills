# 业务规则：抖音公开数据回收

## 发布触发

- “明确发布”必须是人类完成式陈述，不包括计划、催问、预览、待发布、审核通过或机器人转述。
- 群内真实 `@0615`、明确发布语义和唯一抖音作品链接三者同时存在才创建 Publication。
- 当前固定 `required_platforms = [douyin]`；不补建视频号或其他平台任务。
- `published_at` 优先采用公开作品数据的 `create_time`。排程阶段尚未读取时以触发消息 `create_time` 暂定，首次窗口必须核对并按实际时间计算快照龄。
- 同一 `video_id` 只建立一个 Publication；重复发布消息只追加证据。

## 2h、6h、24h 与 48h

- 统一使用 `Asia/Shanghai`；`due_at_<window> = published_at + <window>`。
- 四个窗口为精确单次任务，禁止每小时、每日或其他周期轮询。
- 到期 6 小时内记为 `on_time`；更晚补采标记 `late` 并保留实际快照龄。
- 首次公开接口回读发现实际发布时间晚于暂定时间、导致当前采集尚未到期时，不写快照，按实际到期时间重新排程未完成窗口。

## 指标与证据

- 数据源仅限抖音匿名公开分享页及同一匿名公开数据链路；禁止浏览器、账号后台、Cookie 和登录态。
- 当前稳定公开指标为点赞、评论、分享、收藏；其他计数只有接口真实返回且语义明确时才记为可用。
- 公开接口中的 `play_count=0` 是不公开播放量的常见占位值，必须标记 `unavailable`，不能记为真实 0。
- 曝光、观看人数、平均观看时长、完播率、跳出率、回看率、跳过率、流量来源、观众画像、主页访问和新增关注等后台专属指标一律标记 `unavailable`。
- 每个窗口至少保存一份带采集时间、内容 ID、标题和原始统计字段的 JSON 证据。失败是 `collection_failed`，缺失是 `unavailable`，均不得填 0。
- 每个窗口同时保存匿名公开评论与全时长弹幕快照。第一份真实快照作为变化基线；后续窗口用内部稳定键计算新增记录，但交付物不得包含这些键或任何用户 ID。
- 评论与弹幕变化至少覆盖新增量、好评、差评、明确问题、重复话题频次和弹幕时段密度；未采集的历史窗口不得补造。

## 幂等、文档与网页

- 幂等键固定为 `publication_id:2h/:6h/:24h/:48h`；已有同一快照且一致时不重复写，不一致时返回 `write_conflict`。
- 同一项目只维护一篇 `<项目名>-数据回收` 飞书文档；四窗口追加到同一对比表，不覆盖历史。
- 同一 `video_id` 只维护一个飞书妙搭 HTML 应用。新窗口更新原应用，保留稳定 URL；不同作品不得共用或覆盖应用。网页必须包含可操作的指标/窗口/评论弹幕切换与图形对比，不得把静态数字页称为互动网页。
- 妙搭页面必须公开免登录，并在发送回执前完成未登录 HTTP 回读。

## 群内回执

- 每个窗口只有快照、文档和网页全部回读成功后，才向原发布群发送一次阶段回执。
- 48h 回执同时承担最终复盘回执，不再发送第五条。
- 回执按 `project_id:<window>:group_receipt` 去重；重跑不得重复发群。
