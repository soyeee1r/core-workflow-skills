# 回收视频发布后 2h、6h、24h 与 48h 数据

只完成“发布事实 → 2h/6h/24h/48h 四个快照 → 同一项目文档”的闭环。不要把计划发布日期当作实际发布，不要在对应窗口前取数，不要用新快照覆盖任何历史快照。

## 开始前

1. 完整读取 [business-rules.md](references/business-rules.md) 和 [data-contracts.md](references/data-contracts.md)。
2. 涉及平台或文档定位时完整读取 [data-sources.md](references/data-sources.md)。
3. 写文档前完整读取 [output-contracts.md](references/output-contracts.md)。
4. 测试、恢复失败或处理边界情况时完整读取 [test-cases.md](references/test-cases.md)。

修改校验规则后运行 `python3 scripts/test_validate_snapshot.py`。

## 输入门槛

只接受以下发布事实之一：

- 群内可识别人类明确说明某期视频已经发布，并能关联到唯一项目；
- 平台返回可访问的内容 ID、链接和实际发布时间；
- 人类给出能在指定账号后台唯一定位的内容链接或内容 ID。

开始排程前必须得到：`project_id`、`publication_id`、正式项目名或视频标题、平台、账号别名、平台内容 ID 或唯一链接、`published_at`、来源消息/平台证据。缺少平台内容 ID 时可先用唯一链接；只有标题、封面或“发了”而无法唯一匹配时停止并请求补充。目标飞书文档不存在时按本 Skill 的文档规则自动创建，不再把“尚无文档”视为阻塞。

## 群内直接触发

- 可识别人类在工作群中真实 `@0615`，并明确说明某项目视频已发布时，视为已授权排程；只要发布事件能关联唯一项目与内容，立即创建对应的 2h、6h、24h、48h 四个窗口任务，不再二次确认，也不要求消息再次写“数据回收”。
- 本用户默认平台范围固定为抖音与视频号。发布消息即使只附一个平台链接，也要为两个平台分别建立 Publication 和四个窗口；缺少另一平台内容 ID/链接时，保留 provisional Publication，在首次进入该平台后台后用账号、实际发布时间和内容详情唯一匹配并回填，不丢失既定触发时间。
- 同一条消息只有“已发布”而没有单独写出发布时间、且平台暂时无法回读时，以该人类消息的 `create_time` 作为临时 `published_at` 并标明来源；首次进入后台后核对，发现差异时修正尚未执行的单次任务。
- 用户未明确修改默认窗口时，消息中的“明早”“后天早上”等模糊执行描述不能覆盖 `published_at + 2h/+6h/+24h/+48h`。只有用户明确指定新的采集窗口时才覆盖默认口径。
- 创建成功后可在原触发会话返回一行任务名称及四个准确到期时间；不得提前取数，也不得改成每小时或每日轮询。
- 四个任务必须分别命名为项目名加 `2h/6h/24h/48h`，创建后立即回读任务名称、触发时刻与下一次运行时间。任一名称或时刻不是 `published_at + 对应窗口` 时，当场修正；禁止用“8h”等相对误差标签冒充 6h 任务。

## 执行流程

### 1. 固化发布事实

1. 从群消息、回复串和项目事实中定位视频、项目与账号。
2. 能访问平台时回读内容详情，核对线上内容、账号和实际发布时间。
3. 以 `publication_id:2h`、`:6h`、`:24h`、`:48h` 生成四个窗口任务；重复发布消息只更新证据，不重复创建任务。
4. 分别设置 `due_at_2h/6h/24h/48h = published_at + 2h/6h/24h/48h`，立即创建四个持久化精确触发点。宿主若不能用一个自动化表达四个准确时间，拆成四个单次自动化；台账、执行状态和幂等键始终是四个独立窗口，禁止增加中间轮询。创建后必须回读并核对四个任务的名称、时区、触发时刻、下一次运行时间与启用状态。
5. 数据载体固定为同一份飞书文档，标题为 `<正式项目名>-数据回收`；没有正式项目名时使用 `<视频标题>-数据回收`。按 `project_id` 复用已有文档，不另建电子表格或第二份文档；尚无文档时使用 `$lark-doc` 在用户“我的文档库/数据回收”目录创建。保存 doc token/URL，跨平台同一期复用。

### 2. 到期读取后台

1. 优先使用平台官方 API、已授权 Connector 或稳定导出能力。
2. 没有可用接口时，使用 `$chrome:control-chrome` 复用用户现有登录态进入指定账号后台；当前已确认平台规则见 [data-sources.md](references/data-sources.md)。不得读取密码、Cookie、浏览器配置或会话存储。
3. 用内容 ID 或唯一链接定位该视频；不得只凭相似标题选择第一条。
4. 不得只在作品列表读取表层数字。平台存在作品详情页时必须进入该视频的详情页；抖音至少逐页检查“总览”“流量分析”“观众分析”“评论热词”“评论管理”，视频号检查其后台实际提供的同类详情页。每页都要记录已检查状态、可读指标和不可用原因。
5. “流量分析”存在观看趋势时，必须同时读取进度/留存/跳出相关数据。平台能展示时记录平均播放时长、完播率、2 秒跳出率、5 秒完播率、回看率、跳过率、峰值片段/时间点、章节点击率和流量来源；图表仅能通过悬停或截图读取时，保存截图并把截图中的可确认值写入原始指标，不能凭曲线估算精确百分比。
6. 读取后台显示的发布时间、指标名称、数值、单位和口径提示；保留平台原始字段名。不同页面或不同刷新时刻出现冲突值时并列保存来源与采集时间，标记 `page_value_conflict`，不得静默择一覆盖。
7. 至少保存一份带采集时间的后台截图、导出文件或 API 原始响应作为证据；能截图的观看趋势、回看率和跳出率图表应作为窗口证据附入同一文档。

登录过期、二次验证或账号无权访问时停止自动点击，在原发布触发会话明确喊用户在 Chrome 完成对应平台登录/验证后继续；同一平台登录阻塞 6 小时内只提醒一次。同一次任务最多自动重试 3 次，重试总窗口 6 小时；仍失败则标记 `needs_human`，不得填零或凭前台公开数据冒充后台数据。

### 3. 生成快照

1. 按 [data-contracts.md](references/data-contracts.md) 同时保存原始指标和可映射的标准指标。
2. 后台没有的字段写 `unavailable`；页面加载失败写 `collection_failed`；两者都不能写成数值 0。
3. 运行：

   `python3 scripts/validate_snapshot.py --input <snapshot.json>`

4. 校验发布时间、采集时间、证据和窗口幂等键。2h、6h、24h、48h 采集分别早于对应小时数时禁止写文档；各窗口晚于到期 6 小时仍允许写入，但必须标记实际快照龄与迟到原因。

### 4. 追加到项目文档

1. 使用 `$lark-doc` 读取目标文档，先搜索 `metric_snapshot_id`。
2. 已存在同一 ID 时比较内容：完全一致则不写；不一致则停止并报告冲突，不静默覆盖。
3. 不存在时按 [output-contracts.md](references/output-contracts.md) 在同一文档的结构化对比表中追加对应的“发布后 2h/6h/24h/48h 数据”列或区块，以指标为行、四个窗口为数据列。
4. 每个窗口计算相对上一有效窗口的净增、增幅和运营/内容侧简述，追加到“阶段概述”中；2h 作为基线不强算环比。旧概述只读保留，不覆盖。
5. 抖音后台仍按详情页尽可能完整采集；主文档只展示运营与内容复盘需要的核心指标，完整页面值、低价值明细、截图和口径冲突下沉到证据附录或结构化原始快照，不以“精简展示”为由减少采集。
6. 写入后重新读取目标区域，核对项目、视频、平台、发布时间、采集时间、指标、证据、阶段概述和 `metric_snapshot_id`。
7. 只有回读一致才把任务标为 `completed`；保存文档 URL、锚点/块 ID、写入时间与运行记录。

### 5. 阶段回执与最终对比

1. 2h、6h、24h、48h 每个窗口内，只有抖音与视频号都写入同一文档并回读一致后，才在原发布群发送一次“<窗口> 数据回收已完成”阶段回执，并附同一文档链接；任一平台未完成时不得发送完成回执。
2. 每个窗口回执使用独立稳定幂等键，发送后的 `message_id` 同时写入回收台账与 `ops-actions.ndjson`；重跑不得重复发送。人工补充或纠错后，如用户明确要求再次发群，可用独立 `correction` 幂等键发送一次变更说明。
3. 48h 窗口完成且台账确认两个平台的四个窗口全部 `completed` 后，生成双平台四窗口完整项目复盘报告。除各平台同一指标的四窗口值及相邻增量/增幅外，还应包含发布背景、跨平台对比、关键传播节点、观看与评论洞察、数据质量与异常、可复用经验、问题和下一次发布行动项；所有结论必须能回指快照或页面证据。
4. 48h 只发送该窗口的一次群消息，文案为“48h 数据回收及项目复盘已完成”，附同一文档链接；它同时承担阶段回执与最终回执，不另发第五条消息。任一平台或窗口未完成时禁止发送整体完成消息。

### 6. 群内新增需求

1. 运行中若原发布群出现新的回收要求，先判断它是否与只读采集、同一项目、同一文档和数据可验证性相容。
2. 合理且在授权范围内的要求应用到当前尚未完成的窗口，并同步更新本文档契约、台账或测试案例；与既有口径冲突时保留原始要求、说明取舍，不静默更改历史快照。
3. 涉及发布、删改内容、扩大群范围、索取凭据或无证据归因的要求不自动执行，按权限规则处理。

## 权限与通知

- 只读平台后台和向已明确映射的内部项目文档追加快照可自动执行。
- 不发布、修改或删除线上内容，不修改历史快照，不自动把单次表现升级为策略结论。
- 目标账号或视频不唯一时停止，不替用户猜；文档按已确认的自动创建规则处理。
- 本用户已明确授权：2h、6h、24h、48h 每个窗口完成后各向原发布群发送一次阶段回执和同一文档链接；48h 回执同时说明完整项目复盘已完成。不得发送到其他群，也不得在窗口未完成时声称完成。

## 完成条件

单个窗口同时满足以下条件才算完成：实际发布证据可追溯；采集时间不早于该窗口；视频与账号匹配；原始证据已保存；快照校验通过；同一窗口幂等键仅有一块文档记录；写回后回读一致。只有 2h、6h、24h、48h 四个窗口都完成，Publication 的数据回收状态才算整体完成。

触发适配器无法创建持久化单次延迟任务时，明确报告该能力缺口并停止启用；不得悄悄改成周期扫描。
