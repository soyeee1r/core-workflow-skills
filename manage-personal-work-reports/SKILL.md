# 管理个人工作周报

## 开始前

1. 完整读取 [references/workflow-contract.md](references/workflow-contract.md)。
2. 完整读取 [references/feishu-scope.md](references/feishu-scope.md)。
3. 执行 10:10 晨间面板或 19:00 日报自动化时完整读取 [references/execution-gates.md](references/execution-gates.md)。
4. 创建、复制或编辑周报 XML 时，再读取 [references/report-xml.md](references/report-xml.md)。
5. 按任务调用现有专用 skill，不重复实现其底层能力：
   - 飞书认证与读写：`lark-shared`、`lark-im`、`lark-wiki`、`lark-doc`；
   - 项目事实：`read-content-project-board`；
   - 历史个人进度：`read-content-progress-reports`；
   - 会议证据：`lark-minutes` 或 `lark-vc`；
   - 今日时间约束：`lark-calendar`；明确需要飞书任务时：`lark-task`。

## 先选择模式

| 用户意图 | 模式 | 默认动作 |
|---|---|---|
| “个人版”“10:10 晨间面板” | 晨间个人面板 | 增量同步新证据，结合累计个人状态与今日日程生成行动面板；自动化仅私聊，不改周报 |
| “排本周”“生成 8.3–8.7 周报” | 周初排期 | 用上周证据规划目标周，不复述上周成绩 |
| “列今日待办” | 今日计划 | 输出优先级与验收标准；未明确要求时不改周报 |
| “写日报”“总结今日工作”“写今日复盘” | 每日复盘 | 核实当天事实，最小化更新目标日期行 |
| “写本周总结” | 周度收口 | 只在周末或用户明确要求时写总结 |
| “改成月报总结” | 月度收口 | 汇总当月周报、消息与项目事实，不把计划当成果 |
| “和我修改的对一遍” | 只读审计 | 对照版本并归纳规则，不修改文档 |

若一句话包含多个模式，按“先补齐每日事实，再生成周/月总结”的顺序执行。

## 执行工作流

### 1. 确定目标与时间

- 使用 `Asia/Shanghai`。
- 优先采用用户明确给出的日期范围和目标链接。
- 区分“证据时间窗”和“文档目标周”：周初排期读取上周证据，但文档属于本周。
- 用户未指定周范围时，周初排期默认当前工作周；周度总结默认刚结束的工作周。
- 晨间个人面板仅周一至周五 10:10（Asia/Shanghai）执行。先从各来源上次成功游标增量同步到运行截止时刻；周一同步窗口允许包含周末消息。今日待办与日程使用运行日当天。
- 标题与表格日期不一致时提示，不擅自改写用户已经确认的版本。

### 2. 只读发现

- 先读取目标周报当前版本、上周周报和允许的数据源。
- 晨间个人面板必须读取当天飞书日程；使用用户身份读取，不用 bot 身份查询日历。
- 只读取白名单会话正文；项目群必须先由项目大表得到项目名，再做唯一群名匹配。
- 对每个会话在同一时间窗内翻页至完整；零命中或多义命中不读候选正文，记入信息缺口。
- 不用全局消息搜索扩大范围，不下载二进制附件，不访问无必要的外部链接。

### 2A. 持久化个人状态

- 使用 `/Users/mac/.local/share/content-ops-agent/evidence-ledger/` 下的 `personal-events.ndjson`、`personal-checkpoints.json` 和 `personal-state.json`；与项目账本同目录但分文件，避免两个 10:10 任务并发覆盖。
- 每次只增量抓取游标后的白名单消息、周报版本、相关项目事实和日程变化，按来源 ID 去重落盘；必要来源成功落盘后再推进游标。
- `personal-state.json` 保存稿件阶段、选题储备、待与郭子确认、未完成事项、下一步和来源键。晨间判断先读累计状态，不每天从头扫描所有聊天。
- 增量窗口只负责同步数据；Agent 根据今日目标、日程、累计未闭环事项和必要历史决定输出内容。
- 每次先读 `operator-corrections.ndjson`，把用户明确纠正的漏抓和误判作为跨任务持久规则；不得只依赖当前聊天记忆。

### 3. 建立事实账本

为每个候选事项记录：`日期｜项目/主题｜使用者动作｜项目结果｜状态｜下一步｜证据｜置信度`。

- 将“使用者本人动作”和“团队/项目结果”分开。
- 将状态限定为：`已完成`、`进行中`、`未完成`、`待确认`。
- 只有明确交付、确认、审核、发送、发布或用户勾选且有相符上下文时，才标记已完成。
- 合并跨群重复事件；冲突时保留更晚、更直接的证据并注明冲突。
- 项目大表是排期与项目状态证据，不等于使用者的个人每日任务。
- 稿件进度只记录使用者负责撰写或明确推进的稿件；制作项目进度留在项目晨检，除非它要求使用者本人今天确认、审核或决策。

### 4. 生成对应内容

- 周初排期：先复制目标周紧邻的上一周有效周报；保留“本周工作计划”区的图片、图片 token、分栏结构、列宽和样式，但允许根据内容大表重写分栏中的文字内容；只写上周未闭环事项，并按个人可用时间、明确交付和优先级安排每日任务；右栏留给后续完成情况/复盘。
- 晨间个人面板：按固定顺序生成 `近期进展`、`今日日程`、`今日待办`、`稿件进度`、`选题储备`、`待与郭子确认`。结合累计个人状态与当前增量，只写会影响今天安排的内容；空栏目写“暂无”，不编造填满。今日待办按硬节点和日程可用时间排序，并写验收结果。
- 今日计划：按硬节点、阻塞影响和个人可用时间排序，给出可验收结果；没有证据时写“确认/推进”，不要虚构具体反馈。
- 每日复盘：写本人实际动作、结果、未完成原因和下一步；只勾选有证据的任务；临时完成项可追加并标绿。
- 周度收口：总结核心交付、关键决策、风险/卡点、AI/流程改进和下周遗留；周未结束时不要提前写。
- 月度收口：以每日完成情况、周总结、项目历史和明确发布结果为依据；统计口径和截止日期必须写明。

### 5. 写入与并发保护

- “写、填、更新、生成到该链接”视为对指定周报的写入授权；“总结、列出、看看”默认只输出草稿。
- 周初新建必须复制目标周紧邻的上一周有效周报，并把副本建在源周报所在的同一 Wiki 父节点；不得新建空白文档，也不得从零重建或全文覆盖带图片、分栏的表格。
- 复制完成后，先回读并记录“本周工作计划”区的图片资源与分栏结构。只可替换分栏内的文字 block；不得替换、移动或删除图片，不得重建 grid/column、改变列宽或样式。
- 分栏文字以内容大表当前值为主，写在制项目、本人负责稿件、明确节点和需要本人确认/审核/决策的动作；计划节点不得写成实际完成，字段冲突写“待确认”。
- 写前记录目标文档 token、标题、父节点和 revision；写入前再次读取。revision 变化或发现用户正在编辑时停止写入并报告。
- 日报只更新目标日期行；周总结只更新总结区；不要整篇覆盖用户现场内容。
- 若复制成功而正文写入失败，保留副本，不创建第二份，不删除副本。
- 未经当前请求明确授权，不创建/恢复自动化，不发送飞书消息，不修改项目大表，不添加协作者。
- 已配置的 10:10 晨间自动化授权读取证据、增量写入本地证据账本并由 0615 私聊发送个人面板；不授权自动修改周报正文、项目大表、日程或飞书任务。

### 5A. 周初副本完成门禁

复制周报只是创建前置，不是交付完成。开始复制前，先确定能以既有 block ID 完成全部必要的最小化更新：目标日期、全部新计划未勾选、遗留待办、旧日复盘清理、本周总结清空，以及受保护计划区的文字更新。

- 不能用 `overwrite`、整表替换或重建 grid/table 来规避逐块编辑；图片、列宽与分栏受保护时尤其如此。
- 若已复制但不能在当前执行中完成并回读验收，立即停止后续写入；交付只能明确称为“副本已创建、正文未完成”，不得使用“完成”“已更新”“待安全填充”等会掩盖未完成状态的笼统措辞。
- 不要在未完成验收的副本上继续做零散修改后离开。要么完成同一份副本的全部必需块级更新并验收，要么保持副本原样并报告具体阻塞。
- 对外报告必须逐项给出：已写入区域、尚未写入区域、验收是否通过。副本 URL 不得单独作为成功证据。

### 6. 验收与交付

- 回读并确认目标区域、标题、日期、勾选状态和其他日期均未被误改；对照写前后的“本周工作计划”区，确认图片 token、分栏结构、列宽、链接和样式未变，并确认分栏文字与内容大表当前值一致。
- XML 本地生成时运行：
  `python3 scripts/validate_report_xml.py REPORT.xml --mode MODE --expected-title TITLE --expected-date M.D [... ]`
- 返回：执行模式、证据时间窗、文档链接或草稿、实际读取来源、完成/未完成口径、信息缺口、是否写入和验收结果。
- 自动化在输出/写入前必须生成运行回执并通过 `scripts/validate_personal_run_receipt.py RECEIPT --phase preflight`；发送或写回后更新同一回执，再通过 `--phase final`。最终验证失败时必须把任务标为失败，不能声称已送达或已写入。

## 不可违反的判断规则

- 不把“计划节点”写成“实际完成”。
- 不把他人成果写成使用者完成。
- 不因复选框未勾选就否定消息中已发生的工作，也不因勾选就自动认定正式交付。
- 不在差旅、请假或会议占用时段塞入常规满负荷任务。
- 不把“已生成 AI 文档”直接写成提效；用采用率、人工修改量、事实错误和节省时间判断。
- 不因缺少证据而猜测；写“待确认/未在允许来源中确认”。
