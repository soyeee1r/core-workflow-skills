01 / A CONTENT WORKFLOW

四个技能，
把内容工作连起来。

读懂外部信息，安排今天的行动，收回作品的反馈。把零散结果留成下一次决策可用的证据。

01X 链接读取外部信息 → 有来源的理解02个人助理累计进展 → 今日行动03抖音爬楼评论与弹幕 → 观众反馈04定时数据回收四个时间窗口 → 项目复盘

本说明展示工作方法与技能规则，不代表所有环节已自动串联或定时任务正在运行。

02 / THE WHOLE PICTURE

从信号到行动，再回到判断。

发布前处理“值得做什么、今天做什么”；发布后处理“观众说什么、数据说明什么”。

技能内部明确的处理流程人工衔接或按需调用，非自动触发

05 / DOUYIN-COMMENT-COLLECTOR

爬楼，看观众究竟在反馈什么。

群内一至五个抖音链接 + 真人 @0615 + “扫楼”。每个作品独立采集、整理和交付。

COMMENTS / 评论与回复

100 + 50 / 批

100 条起步，每 50 条评估信息增量。连续两批低增量时停止，最多 500 条。

公开可见范围不足时据实报告，不用重复内容补数。

DANMAKU / 全时长弹幕

≤ 32 秒 / 段

按视频全时长逐段读取、合并与去重。只有完整读取为空，才能把弹幕记为 0。

评论与弹幕分别保留原始证据，再形成联合报告。

按质量筛选高互动 · 好评 · 明确问题 · 重复话题
一篇联合报告归档飞书“查水表”
一张群卡片视频标题 + 关键结论 + 文档链接

读取量与展示量分开；不固定凑满十条。现行采集不使用浏览器或用户 Cookie。

06 / COLLECT-CONTENT-PERFORMANCE-DATA

在四个时刻，记录作品如何变化。

以实际发布事实为起点，分别回收抖音与视频号后台数据，持续写入同一份项目文档。

时间示例：北京时间 9 月 10 日 10:00 发布。下列为到期时刻示意，不是已创建的任务。

2h / 建立第一份有效快照

两平台分别读取作品详情与实际可用的总览、流量、观众和评论信息；保留证据。此时是基线，不强算环比。

2 平台 × 4 窗口

每个平台单独保存发布记录与快照。

一份项目文档

追加窗口数据，历史快照不覆盖。

完成后再回执

同窗口两平台均写入并核对后，才发完成消息。

07 / WHAT MAKES IT WORK

四个入口，背后是三层支撑。

业务层 · 决定做什么X 读取 / 个人助理 / 抖音爬楼 / 数据回收
能力层 · 完成具体操作本地采集与校验脚本、飞书技能、平台 API 或受控浏览器
运行层 · 记住并按时执行账号权限、明确的数据范围、状态账本、持久化调度

每一步，都要能回答四件事。

1

输入来自哪里？

2

实际做到哪一步？

3

产物在哪里？

4

怎么核对已经完成？

读取用用户身份、指定群消息用机器人身份；具体以各技能规则和本次授权为准。会议整理、项目晨检等是另外的工作流，本仓库不捆绑它们。

08 / PUT IT INTO PRACTICE

从一个真实请求开始。

X 链接读取

“这个 X 链接讲了什么？图里有哪些补充信息？”

个人助理

“结合今天日程和未完成事项，列出今日待办。”

抖音爬楼 · 在目标群发送

“<抖音链接> @0615 扫楼”

数据回收 · 唯一项目与发布事实

“@0615 这期已发布：<作品链接>，按 2/6/24/48h 回收数据。”

让每次读取，
留下可追溯的理解。
让每次复盘，
接得住下一步行动。

安装文件 ≠ 登录账号 ≠ 启用自动化。先准备依赖与本人配置，再按照真实请求执行；失败和缺口应明确保留。
